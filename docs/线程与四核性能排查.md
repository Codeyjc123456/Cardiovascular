# 线程与四核性能排查（2026-09-05）

本次基于源代码检查并实施修改。尚未取得工作机的 CPU、内存、线程栈、串口时序或异常日志，不能据此认定“核心数少”就是功能异常的根因。普通 Thread 的委托返回后线程会结束，不需要显式销毁；本项目找到的显式线程主要是一次性查询、生成报告和延迟操作，没有发现它们自身存在永不退出的循环。

更值得关注的是界面同步等待、重复任务并发、串口接收阻塞、跨线程操作图表、定时器存活和资源清理竞争。单纯把 Thread 改成 Task.Run，仍会把 Sleep、同步网络等待转移到线程池中，不能自动解决这些问题。

数据库查询和报表库仍然是同步操作，Task.Run 让它们在工作线程运行。已经开始的这类操作不会被强制终止：列表通过丢弃过期结果避免污染界面，报告通过等待结束再清理避免释放正在使用的对象。

## 仍然存在、应优先设备联调的风险

1. **串口接收回调仍执行长耗时业务。** SerialPortManager.serialPort_DataReceived 直接调用 ReciveAlarm；MeasurePage 的 HandleBPData、HandleAIPulseData、AlltestStopWhenPWVfail 和 ReciveAlarm 中仍有 200–2000ms 的 Sleep，且 ProcessData 会进行波形分析。回调占用时间长，接收数据可能积压。这是下一步排查“测量卡住、漏响应”的首要位置。不能为每包数据直接 Task.Run：会造成乱序，并发修改 workStatus、WaitForAck、RpRawData 等状态。应在有串口记录和设备回归条件后，将收包与业务处理分离，使用有界、单消费者队列，并把指令流程改为按应答推进的异步状态机。

2. **设备指令与超时状态没有统一串行化。** SerialPortManager.SendDataToMCU 可能由 UI、定时器、接收回调同时调用；所有命令共享 reciveCounter/reciveCounterMax。接收任意数据就关闭超时计时，压力轮询又可能不断重置它。移除 DiscardInBuffer 只修复明确的丢包点，未解决“哪个应答属于哪个请求”。需以协议为依据建立匹配和超时规则。

3. **停止/卸载不能抢占正在执行的串口回调。** 本次解绑后不会再把新通知派发到旧页面，但已经进入 ReciveAlarm 的同步调用无法由 CancellationToken 强制中断，仍可能在返回前更新旧状态或发送指令。应重点回归测量过程中切换主页面、调试页切换和返回重入。彻底解决需配合上一项的单消费者状态机和会话编号。

4. **调试页还有同步 UI 操作。** cmdCloseValve_Click 仍有 500ms 的指令间隔休眠；DisPlayTips 的 Dispatcher.Invoke 会令串口发送/接收等待 UI；ProcessRp_Click 在 UI 上计算心率。ReciveAlarm 中还保留 300ms 的协议等待。它们未被盲目改成并行任务，以免改变控制顺序或让共享采样集合与计算并发。

5. **调试原始样本仍可能持续增长。** DebugSetPage.ReciveAlarm 向 RpRawData 累加，只有 ClearWave 才重置。显示缓存上限不等于原始样本上限。需明确连续调试允许的时长或分析窗口，再决定自动停止、滚动窗口或落盘，不能无依据截断用于计算的数据。

6. **备用网络路径仍同步阻塞。** ApiBLL.DoPostBase64、DoPostUser、UploadDataPost 仍有 .Result，GetUser 使用同步 WebClient.UploadData；LoginAPPID 为备用同步登录路径。当前 LoginBtn 使用的标准接口已修改，备用路径若重新启用，应沿调用链改为 Task 返回并 await，不能只在最外层套一个线程。

7. **其他页面仍有 GC.Collect 和同步数据库调用。** MainPage、SystemWinPage、DataManageWinPage、Diagnosis、若干注册/设置页仍显式全量回收；部分保存、删除、导出和算法调用还在 UI 线程。全量 GC 不能代替 Dispose/取消订阅，可能造成停顿。需要结合工作机采样判断它们的实际占比，本次未批量删除所有页面逻辑。
